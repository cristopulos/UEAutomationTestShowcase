Automation Showcase

This project demonstrates Unreal Engine's built-in Automation Test system end-to-end with a small stub gameplay “damage system” (UShowcaseDamageSystem) and 13 C++ automation tests — 10 verify correct behavior (including 5 that exercise initial-setup patterns such as transient worlds, latent commands, and shared actor fixtures), and 3 intentionally fail because the gameplay code and one test contain deliberately seeded bugs. The purpose is to show what automation tests are for (catching logic regressions early, documenting intent, enabling CI), how they are written, registered, and run.

Why automation tests

Automation tests are the cheapest, fastest way to keep gameplay math honest as a codebase grows. They run without a human, without rendering, and without a level.

  • Regression protection. A test that passes today locks today's behavior in. When a refactor silently changes a constant or a clamp, the next run turns red and points to the diff.
  • Runnable headless in CI. The same RunTest body that the editor GUI executes can be invoked from a shell with -unattended, -nullrhi, and no windowing system — exactly what a build bot needs.
  • Readable failure messages. TestEqual / TestTrue take a descriptive What string that becomes the human-readable “expected vs actual” line in the report.
  • Executable spec. A passing test suite documents intended behavior in a form that cannot drift out of date, because it is the code.

The gameplay stub

UShowcaseDamageSystem is a UCLASS of pure static UFUNCTION helpers. No actor, no tick, no world needed — which is exactly what makes it ideal for fast, deterministic unit tests.

Spec

  • ApplyDamage(CurrentHealth, IncomingDamage, bIsCriticalHit) — crit doubles damage; result is clamped to [0, CurrentHealth].
  • CanAffordCost(CurrentCurrency, Cost) — true when CurrentCurrency >= Cost.
  • GetDamageTier(Damage) — Low < 25, Medium ≥ 25 < 75, High ≥ 75.
  • CalculateLootBonus(PlayerLevel, BaseLoot) — BaseLoot * (1 + 0.05 * Level).

Header Source/AutomationShowcase/ShowcaseDamageSystem.h

// Copyright Epic Games, Inc. All Rights Reserved.

#pragma once

#include "CoreMinimal.h"
#include "UObject/Object.h"
#include "ShowcaseDamageSystem.generated.h"

/**
 * Self-contained showcase damage system.
 * Pure calculation helpers - no Tick, no components, no actor required.
 *
 * NOTE (showcase): This class intentionally contains two seeded bugs
 * (ApplyDamage crit multiplier and CalculateLootBonus scaling) so that
 * automation tests can be demonstrated failing. See INTENTIONAL-BUG
 * comments in ShowcaseDamageSystem.cpp.
 */
UCLASS()
class AUTOMATIONSHOWCASE_API UShowcaseDamageSystem : public UObject
{
    GENERATED_BODY()

public:
    /** Applies IncomingDamage to CurrentHealth and returns the new health.
     *  Critical hits double the incoming damage (x2.0). Result is clamped to
     *  [0, CurrentHealth] (overkill protection only; negative damage is NOT
     *  guarded - see EdgeCase test). */
    UFUNCTION(BlueprintCallable, Category = "Showcase|Damage")
    static float ApplyDamage(float CurrentHealth, float IncomingDamage, bool bIsCriticalHit);

    /** Returns true when CurrentCurrency >= Cost. */
    UFUNCTION(BlueprintCallable, Category = "Showcase|Damage")
    static bool CanAffordCost(int32 CurrentCurrency, int32 Cost);

    /** Maps a damage amount to a tier label:
     *    "Low"    : Damage < 25.0
     *    "Medium" : 25.0 <= Damage < 75.0
     *    "High"   : Damage >= 75.0 */
    UFUNCTION(BlueprintCallable, Category = "Showcase|Damage")
    static FString GetDamageTier(float Damage);

    /** Returns BaseLoot scaled by player level: BaseLoot * (1.0 + 0.05 * PlayerLevel). */
    UFUNCTION(BlueprintCallable, Category = "Showcase|Damage")
    static float CalculateLootBonus(int32 PlayerLevel, float BaseLoot);
};

Registration pattern

The macro takes the C++ class name, the test's pretty path (used as the filter string when running tests from CLI or GUI), and the test flags. 

// Source/AutomationShowcase/Tests/ShowcaseEdgeCaseTests.cpp (lines 13–17)
IMPLEMENT_SIMPLE_AUTOMATION_TEST(FShowcaseEdgeCasesExactTierBoundariesTest,
    "AutomationShowcase.EdgeCases.ExactTierBoundaries",
    EAutomationTestFlags::EditorContext | EAutomationTestFlags::EngineFilter)

bool FShowcaseEdgeCasesExactTierBoundariesTest::RunTest(const FString& Parameters)
{
    UShowcaseDamageSystem* DamageSystem = NewObject<UShowcaseDamageSystem>();
    TestEqual(TEXT("Zero damage is tier Low"), DamageSystem->GetDamageTier(0.0f), FString(TEXT("Low")));
    // ...
    return true;
}
  • PrettyName — the second macro argument becomes the test's path. CLI filters and GUI search boxes match against this string.
  • EditorContext — the test runs in the editor (and in UnrealEditor-Cmd headless mode), which is what we want for unit-style tests of editor-time gameplay math.
  • EngineFilter — membership in the Engine smoke-filter group; this is what keeps project tests out of unrelated engine smoke-test sweeps.
  • RunTest — the body. Call TestEqual, TestTrue, TestFalse with descriptive What strings; those strings are what shows up in the failure report.

Tests requiring initial setup

The five tests below all pass and they exist to show the initial-setup patterns that real gameplay tests need before any assertion can run: a transient world with its own world context, latent asynchronous commands, and a shared actor fixture that delegates to UShowcaseDamageSystem.

Pattern A — per-test world setup / teardown

Source/AutomationShowcase/Tests/ShowcaseSetupWorldTests.cpp — each test creates its own transient UWorld via UWorld::CreateWorld(EWorldType::Game, false) plus a dedicated FWorldContext through GEngine->CreateNewWorldContext (mirroring Epic's own FTestWorldWrapper lifecycle), spawns actors or components, asserts, and then explicitly tears everything down with UWorld::DestroyWorld(false) and GEngine->DestroyWorldContext so tests never leak state. 

// Source/AutomationShowcase/Tests/ShowcaseSetupWorldTests.cpp (lines 34–55)
static UWorld* CreateShowcasePatternAWorld()
{
    UWorld* TestWorld = UWorld::CreateWorld(EWorldType::Game, false);
    if (IsValid(TestWorld) && GEngine)
    {
        FWorldContext& WorldContext = GEngine->CreateNewWorldContext(EWorldType::Game);
        WorldContext.SetCurrentWorld(TestWorld);
    }
    return TestWorld;
}

static void DestroyShowcasePatternAWorld(UWorld* TestWorld)
{
    if (IsValid(TestWorld))
    {
        if (GEngine) { GEngine->DestroyWorldContext(TestWorld); }
        TestWorld->DestroyWorld(false);
    }
}
  • AutomationShowcase.Setup.WorldAndActorSpawn — spawns a plain actor, asserts it lives in this world (SpawnedActor->GetWorld() == TestWorld), calls Destroy(), asserts it's no longer valid, then tears down the world.
  • AutomationShowcase.Setup.ActorComponentLifecycle — NewObject<UPointLightComponent>(OwnerActor) → OwnerActor->AddInstanceComponent → RegisterComponent (assert IsRegistered()) → DestroyComponent (assert not registered), then OwnerActor->Destroy() + world teardown.

Pattern B — latent asynchronous setup

AutomationShowcase.Setup.LatentTickSequence uses ADD_LATENT_AUTOMATION_COMMAND to enqueue commands that run after RunTest returns. The first command is a pump that increments a shared counter each time its Update() is called (over N frames). The second command is enqueued after it, so the framework's FIFO latent queue guarantees the assertion command runs only after setup completed. The assertion routes through FAutomationTestFramework::Get().GetCurrentTest() so failures still land in the test report. 

// Source/AutomationShowcase/Tests/ShowcaseSetupWorldTests.cpp
// Pump command: completes after N Update() calls.
DEFINE_LATENT_AUTOMATION_COMMAND_ONE_PARAMETER(FShowcasePumpTicksCommand, int32, TicksToPump);

bool FShowcasePumpTicksCommand::Update()
{
    ++FShowcasePumpCounterValue;
    return FShowcasePumpCounterValue >= TicksToPump;
}

// Verify command: reports through the currently-executing test.
DEFINE_LATENT_AUTOMATION_COMMAND_ONE_PARAMETER(FShowcaseVerifyTicksCommand, int32, ExpectedTicks);

bool FShowcaseVerifyTicksCommand::Update()
{
    if (FAutomationTestBase* CurrentTest = FAutomationTestFramework::Get().GetCurrentTest())
    {
        CurrentTest->TestEqual(TEXT("Latent setup ran the pump command once per frame for the expected number of updates"),
            static_cast<float>(FShowcasePumpCounterValue), static_cast<float>(ExpectedTicks), 0.001f);
    }
    return true;
}

bool FShowcaseSetupLatentTickSequenceTest::RunTest(const FString& Parameters)
{
    FShowcasePumpCounterValue = 0;
    const int32 TicksToPump = 5;
    ADD_LATENT_AUTOMATION_COMMAND(FShowcasePumpTicksCommand(TicksToPump));
    ADD_LATENT_AUTOMATION_COMMAND(FShowcaseVerifyTicksCommand(TicksToPump));
    return true;
}

Key point: assertions on async or deferred setup must themselves be latent commands, because the latent queue drains after RunTest returns. Calling TestEqual synchronously inside RunTest would run before any pumping has happened.

Pattern C — shared actor fixture

Source/AutomationShowcase/ShowcaseTargetDummy.{h,cpp} defines a minimal AActor whose ApplyDamageToTarget delegates to UShowcaseDamageSystem::ApplyDamage, so fixture tests can drive the whole chain (world → actor → system) end-to-end. 

// Source/AutomationShowcase/ShowcaseTargetDummy.h (key declarations)
UCLASS()
class AUTOMATIONSHOWCASE_API AShowcaseTargetDummy : public AActor
{
    GENERATED_BODY()
public:
    AShowcaseTargetDummy();
    UPROPERTY(BlueprintReadOnly, Category = "Showcase|Damage")
    float Health = 100.0f;
    UFUNCTION(BlueprintCallable, Category = "Showcase|Damage")
    float ApplyDamageToTarget(float Damage, bool bIsCritical);
};

// Source/AutomationShowcase/ShowcaseTargetDummy.cpp
float AShowcaseTargetDummy::ApplyDamageToTarget(float Damage, bool bIsCritical)
{
    Health = UShowcaseDamageSystem::ApplyDamage(Health, Damage, bIsCritical);
    return Health;
}
  • AutomationShowcase.Setup.ActorFixtureAppliesDamage — builds a transient world + spawns the dummy + a shared UShowcaseDamageSystem, then calls TargetDummy->ApplyDamageToTarget(30.0f, false) on 100 HP and asserts the dummy lands at 70 (the non-crit path).
  • AutomationShowcase.Setup.ActorFixtureCleanupVerifiesDestroy — builds the same fixture, applies one tick of damage, then TargetDummy->Destroy() and asserts !IsValid(TargetDummy).
Why the cleanup test asserts a delta, not an absolute zero. A fresh UWorld from CreateWorld(EWorldType::Game, false) comes with its level pre-populated with a few default actors (notably WorldSettings), and RemoveActor nulls the actor's slot in the level's array rather than shrinking the array. So the test captures a baseline non-null actor count before the spawn and asserts that the count returns to that baseline after Destroy() — the idiomatic way to verify cleanup of a spawned actor in a freshly-created world.
Note on the seeded crit bug: because AShowcaseTargetDummy::ApplyDamageToTarget delegates to UShowcaseDamageSystem::ApplyDamage, the seeded 1.5× crit bug also affects the actor. The fixture tests assert current behavior (and stay non-crit), so they pass — bug-catching is the job of the three intentionally-failing tests in the suite.

How to trigger the tests

Three ways: the in-editor GUI, a headless command line for CI, and a listing-only command.

a. In-editor GUI

  • Window → Test Automation (or Tools → Session Frontend → Automation tab).
  • Type AutomationShowcase into the filter.
  • Tick the individual tests, or tick the top-level AutomationShowcase node to select everything.
  • Press Start Tests. Results appear in the same window; failures turn red with the verbatim error messages.

b. Command line (headless)

-nullrhi skips rendering entirely, -unattended skips any modal prompts, and -ReportOutputPath / -ReportType=HTML produce an index.html + index.json report alongside the log. The exit code is non-zero when tests fail, which is what makes it usable as a CI gate. 

"/mnt/data/UE 5.7.4/Engine/Binaries/Linux/UnrealEditor-Cmd" \
  "/home/cristopulos/VibeCoding Test/Automation Showcase/AutomationShowcase.uproject" \
  -ExecCmds="Automation RunTests AutomationShowcase; quit" \
  -unattended -nopause -nosplash -nullrhi -log \
  -ReportOutputPath=/tmp/autoshowcase-report -ReportType=HTML
The filter string AutomationRunTests AutomationShowcase matches every test whose pretty-name starts with AutomationShowcase. — exactly the 13 tests in this suite.

c. List tests without running them

"/mnt/data/UE 5.7.4/Engine/Binaries/Linux/UnrealEditor-Cmd" \
  "/home/cristopulos/VibeCoding Test/Automation Showcase/AutomationShowcase.uproject" \
  -ExecCmds="Automation List; quit" \
  -unattended -nopause -nosplash -nullrhi -log

d. Building the code first

If the editor target isn't already compiled, run UnrealBuildTool before invoking the test command above. 

"/mnt/data/UE 5.7.4/Engine/Binaries/ThirdParty/DotNet/8.0.412/linux-x64/dotnet" \
  "/mnt/data/UE 5.7.4/Engine/Binaries/DotNET/UnrealBuildTool/UnrealBuildTool.dll" \
  AutomationShowcaseEditor Linux Development \
  -project="/home/cristopulos/VibeCoding Test/Automation Showcase/AutomationShowcase.uproject" \
   -WaitMutex
